# Findings

What the study found, judged against the hypotheses committed before the
full run ([docs/hypotheses.md](../docs/hypotheses.md)). Every number comes
from [results.csv](results.csv) via [summary.md](summary.md) (generated by
`scripts/plot.py`), or from the side experiments in
[../experiments/](../experiments/).

**Setup.**
- **Machine:** Intel Core i9-14900HX, pinned to one performance core (48 KB
  L1d, 2 MB L2, 36 MB shared L3), Windows 11, Balanced power plan, on AC power.
- **Build:** g++ 16.2 at `-O3`.
- **Coverage:** 12 variants × 6 workloads × n = 2^10…2^24 × 3 seeds, 3,078
  rows. All variants agree on every checksum.
- **Measurement quality:** the median spread between timed reps is 1.0%, and
  between seeds 0.7%. The drift-monitor canary stayed between 20.60 and 20.77
  ns/op across the whole dataset.
- **Provenance:** see [discarded/README.md](discarded/README.md) for what was
  re-measured and why.

**Two kinds of measurement.** *Work* is counted exactly by an instrumented
run: parent-array reads and writes, the path length per find, and the final
tree depth. It is machine-independent; a clang build with Microsoft's
standard library reproduces every count bit for bit. *Time* is measured on the
uninstrumented code. Explanations below are labelled **measured** when an
experiment isolated the cause, and **inferred** when they are the most
plausible reading of the data. No hardware performance counters were
available, so cache misses and branch mispredictions were never counted
directly.

## Headline

1. **The theory predicts the work exactly.** Measured path lengths match
   closed-form expectations for the worst cases: Θ(n) for naive linking and
   Θ(log n) for rank/size linking (to 4 decimal places at n = 2^24). With
   balanced linking and compression they stay flat from 2^10 to 2^24.
2. **The theory does not predict the time.** With work flat (reads per op
   ×1.01), time per op grows **3.0–3.7×** from n = 2^10 to 2^24, in steps that
   line up with the cache sizes. Past L3 the cost per parent-array read is
   3.2× what it is in L1.
3. **Path halving is the best find policy**: fastest in 149 of 180
   (workload, linking, n) configurations, and it also does the fewest reads
   of the compression policies. Two-pass full compression, the textbook
   version, is fastest in only 6 configurations, never by more than 5%.
4. **Three measurement pitfalls each changed results by 2–7,000×.** Each was
   found, fixed, and is reproducible with a flag (H7–H9).

## Verdicts

| | Hypothesis (short) | Verdict |
| --- | --- | --- |
| H1 | Work follows the theory | **Supported** |
| H2 | Time does not follow the theory; the rise tracks the caches | **Supported** |
| H3 | Locality alone explains much of H2 (`local-shuffled` ≥ 2× slower at 2^24) | **Refuted**: 1.33× |
| H4 | Which compression matters little; one-pass ≥ two-pass | **Partly**: halving yes, splitting no; spread up to 42%, not < 25% |
| H5 | Rank beats size at large n, because it is smaller | **Mostly refuted**: only on `kruskal`; size wins at small n |
| H6 | naive + compression < 3× slower than rank + compression on `random` | **Supported** (max 2.78×, and rising) |
| H7 | Without the sink, naive+none looks fastest | **Supported** |
| H8 | A replayed sequence is learned by the branch predictor (not pre-registered) | **Supported** |
| H9 | Windows power throttling made results order-dependent (not pre-registered) | **Supported** |

## H1. Work follows the theory: supported

Figure: [figures/theory.png](figures/theory.png).

| Case | Prediction | Measured |
| --- | --- | --- |
| `chain`, naive+none | mean path per find = n(n−1)/2 ÷ (3n−2) | 2^10: **169.4** (theory 170.6); 2^15: **5,475.5** (theory 5,461.3). Grows 32.3× for 32× n |
| `binomial`, rank+none and size+none | n·log2(n)/2 ÷ (3n−2) | 2^24: **4.00003** (theory 4.00000). rank and size are identical (every merge is a tie) |
| `random`, rank+full | flat (α(n) ≤ 4) | 0.604 → 0.621 from 2^10 to 2^24 (log-log slope 0.001) |
| `kruskal`, rank+full | flat | 0.930 → 0.953 (slope 0.000) |
| `random`, naive+full | grows, at most logarithmically | 1.10 → 2.12: about +0.07 per doubling of n, i.e. logarithmic |

The theory lines are not fitted: they are exact expectations derived from
how each workload is built. For example, in `chain` the n − 1 unites only
ever find roots (depth 0), and the n finds hit a uniformly random node of a
path of length n − 1. The small mismatch at 2^10 and 2^15 is sampling noise
in the n random find targets.

## H2. Time does not follow the theory: supported

Figures: [figures/time_vs_work.png](figures/time_vs_work.png),
[figures/random.png](figures/random.png).

On `random`, every rank/size + compression variant does the same work per
operation at every n (reads ×1.01–1.02 from 2^10 to 2^24). Time grows
3.0–3.7×. rank+full, stepping through the cache levels (its arrays take 5
bytes per element, so L1/L2/L3 fill at n ≈ 2^13.3 / 2^18.7 / 2^22.8):

| Range of n | Arrays live in | ns/op | ns per read |
| --- | --- | --- | --- |
| 2^10 – 2^13 | L1 | 18.8 – 19.4 | 3.4 – 3.6 |
| 2^14 – 2^18 | L2 | 19.9 → 23.2 | 3.6 → 4.2 |
| 2^19 – 2^22 | L3 | 25.6 → 39.4 | 4.6 → 7.1 |
| 2^23 – 2^24 | DRAM | 53.1 → 60.5 | 9.6 → 10.9 |

**Why (inferred):** the operation count does not change, but where the data
comes from does. The steepest rise is between 2^21 and 2^23, as the arrays
outgrow the 36 MB L3. Two observations about the end points:

- **At 2^24 it is cheaper than one cache miss per read would suggest.**
  60.5 ns/op is ~41 ns more than the cache-resident cost, for ~5.5 reads.
  Many of those reads are re-reads of lines just loaded (the root, and full
  compression's second pass), and the two finds in each operation are
  independent, so the CPU can have several misses in flight at once.
- **At 2^10 the cost is not memory at all.** 19 ns for ~5.5 L1-resident
  reads is several times L1 latency. H8 suggests the rest is branch
  mispredictions: when one sequence is replayed and its branches can be
  learned, the same work costs 5.4 ns instead of 19.2, i.e. ~72% of the
  small-n cost disappears. So "constant time per operation" is constant at
  roughly 19 ns in cache and 60 ns out of it.

## H3. Locality alone explains a large part of H2: refuted

Figure: [figures/locality.png](figures/locality.png).

`local` and `local-shuffled` perform identical work (the tests check this,
counter for counter, and the study data confirms it at every n). Their time
ratio, over the 6 rank/size + compression variants:

| n | 2^10–2^14 | 2^16 | 2^18 | 2^20 | 2^22 | 2^24 |
| --- | --- | --- | --- | --- | --- | --- |
| shuffled ÷ local | 1.00–1.01 | 1.02 | 1.04 | 1.11 | 1.25 | **1.33** (1.31–1.44) |

The "within ~10% while in L2" half of the prediction held. The "≥ 2× at
2^24" half did not.

**Why (inferred, and it was a flaw in the experiment's design):** `local`
only makes *a* and *b* close to each other within one operation. *a* is still
uniformly random across operations. So even `local` jumps to a random cache
line on every operation, and its own time grows 2.8× (rank+halving: 13.9 →
39.4 ns/op), against 4.1× for `local-shuffled` (13.9 → 56.3). Scattering *b*
costs one extra cache line per operation, which is worth 1.33×. Most of the
growth in H2 comes from where successive operations land, not from pairing
*a* with *b*. A workload with sequential *a* would be the experiment that
actually tests locality.

## H4. Which compression matters little: partly supported

Figures: [figures/random.png](figures/random.png),
[figures/kruskal.png](figures/kruskal.png), [figures/binomial.png](figures/binomial.png).

- **One-pass is at least as fast as two-pass:** true for **halving** (fastest
  in 149 of 180 rank/size configurations; every exception but one is on
  `chain`, where compression barely matters because rank/size linking
  already builds a star). **False for splitting**, which is slower than full
  compression in 119 of 180 configurations.
- **Spread among compression policies < 25%:** true for `random` (4–23%) and
  the local workloads, **false for `kruskal` (up to 42%) and `binomial` (up
  to 44%)**. At 2^24 it shrinks to 2–13% on every workload except
  `binomial`, which stays at 22–25%.
- **"Compression vs none" ≥ 2× at large n:** true on `kruskal` (2.4–4.6×) and
  `binomial` (1.8–5.8×), **false on `random` (1.23–1.53×)**. On `random`,
  rank linking alone already keeps trees shallow (path 0.96 at 2^24).

**Why halving wins (partly measured):** it does the fewest reads and writes.
On `random`, halving does 4.0 reads/op, splitting 4.5 and full 5.5. Halving
re-points every other node, splitting every node, and full compression walks
the path twice. Halving's time advantage is largest in cache (e.g. 17.1 vs
19.4 ns/op at 2^10) and shrinks to 3–8% at 2^24 (inferred: the extra reads
re-touch lines that are already in cache, so they cost little once the first
touch of each line dominates).

**Fewer reads is not the same as faster (measured).** On `kruskal`,
rank+none does **fewer** reads than rank+full (5.3 vs 6.1 per op at 2^10)
but takes **2.4× longer** (20.0 vs 8.2 ns). That is at n = 2^10, entirely in
L1. The same happens on `random`: rank+none and size+none do the fewest
reads of any variant (3.5–3.9 per op), yet are slower than every rank/size +
compression variant at every n. What differs is path
length: 1.67 vs 0.93 per find on `kruskal`. **Inferred:** longer, variable-
length dependent chains cost more than their read count suggests, because
each hop must wait for the previous one, and a varying trip count makes the
loop exit hard to predict. Read counts measure work, not latency.

## H5. Rank beats size at large n because it is smaller: mostly refuted

| | n ≤ 2^16 | n = 2^24 |
| --- | --- | --- |
| `random`, size ÷ rank time | **0.93–0.96** (size faster) | 1.00–1.05 |
| `kruskal`, size ÷ rank time | 0.92–1.09 | **1.09–1.15** (rank faster) |
| `local-shuffled` | 0.90–0.93 | 1.01–1.07 |
| reads, size ÷ rank | 0.98–1.00 | 0.98–1.00 |

The two build equally shallow forests (reads within 2%). The predicted
large-n advantage for rank's 1-byte array shows up only on `kruskal`. **Why
`kruskal` and not `random` is not explained by this study.**

The unpredicted small-n result has a **measured** explanation
([experiments/rank_branch.cpp](../experiments/rank_branch.cpp)). Rank's
`if (rank[a] == rank[b]) ++rank[a]` is an unpredictable branch, since ties
are common, while size's `size[a] += size[b]` has no branch. Writing rank's
increment branch-free closes about half the gap at n ≤ 2^12, and nearly all
of it from 2^14. For example, at 2^16: rank 16.0, size 15.2, branch-free
rank 15.3 ns/op.

## H6. Compression without balanced linking: supported

naive + X ÷ rank + X on `random`:

| n | 2^10 | 2^16 | 2^20 | 2^22 | 2^24 |
| --- | --- | --- | --- | --- | --- |
| time (full / halving / splitting) | 1.27 / 1.28 / 1.26 | 1.44 / 1.43 / 1.39 | 1.55 / 1.57 / 1.56 | 1.81 / 1.69 / 2.07 | 2.21 / 2.05 / **2.78** |
| reads (full / halving / splitting) | 1.37 / 1.30 / 1.51 | 1.67 / 1.57 / 1.93 | 1.88 / 1.73 / 2.22 | 1.98 / 1.81 / 2.37 | 2.09 / 1.89 / 2.51 |

Under 3× at every n, as predicted. But the ratio is still rising at 2^24
(work grows logarithmically, as in H1), so "under 3×" is a statement about
n ≤ 2^24, not a bound. In cache, the time ratio is *smaller* than the reads
ratio. Past L3 it is *larger*, because naive's extra reads become cache
misses.

## H7–H9. Measurement validity: all supported

Figure: [figures/validity.png](figures/validity.png). Data:
[validity.csv](validity.csv).

| Pitfall | Effect without the safeguard | Reproduce |
| --- | --- | --- |
| **H7.** No `volatile` sink: the compiler deletes side-effect-free finds | naive+none on `chain` at 2^15: **2.2 ns/op** instead of **15,495**. It looks like the fastest variant, ~7,000× too fast. Variants whose finds write (compression) are unaffected | `uf_bench_nosink` |
| **H8.** One sequence replayed every rep: the branch predictor learns it | rank+full on `random` at 2^10: **5.4 vs 19.2** ns/op (3.5×; 2.6–3.9× across 5 variants). 1.24× at 2^12, 1.03 at 2^14, 1.01 at 2^15, 1.00 at 2^16 | `--replay-same-sequence` |
| **H9.** Windows power throttling (EcoQoS) after ~5 s of load | every variant measured after naive+none at n = 2^15 was **2.30–2.35× slower**, so results depended on variant order | `--allow-power-throttling` |

H7 bit twice. The original harness comment described it, and the study
confirmed it. Then the side-experiment helper `experiments/common.hpp`
reintroduced it by discarding a checksum, which made rank+none look 35%
faster (see [experiments/README.md](../experiments/README.md)). Both H8 and
H9 were found only because a number disagreed with expectations: a 3×
slowdown between two sizes that both fit in L1, and the same measurement
coming out at 21 or 38 ns/op.

## Limitations

- **One machine, one compiler for timing.** Work counts are portable
  (verified with clang + the MSVC standard library); times are not. A
  different CPU will move the cache steps and change small-n branch costs.
- **No hardware counters.** Cache-miss and branch-misprediction explanations
  are inferred from controlled experiments (H3, H8, `rank_branch`), not
  counted.
- **Small-n absolute times depend on code generation.** The same library code
  on equivalent sequences runs about 10% faster in the side-experiment
  programs than in `uf_bench`, because the timed loop is inlined into a
  different caller. Comparisons within one program are consistent;
  differences under ~10% between variants at small n should not be
  over-read.
- **The drift monitor only sees clock speed.** It runs in L2, so
  memory-bandwidth contention from other programs goes undetected. One
  transient case (13–25% at n = 2^19–2^22) was caught only because seeds
  disagreed; the chunk was re-measured.
- **The `local` workload controls within-operation locality only** (see H3).
- **naive+none is capped at n = 2^15** on every workload (it takes seconds per
  run beyond that on `chain`). Some of its curves are therefore short.
- **Noisy points:** 17 of 1,026 (workload, variant, n) points have > 10%
  spread across seeds, mostly at n ≤ 2^11, where one run lasts microseconds.
  The plots use the median of three seeds and show the min–max band.
